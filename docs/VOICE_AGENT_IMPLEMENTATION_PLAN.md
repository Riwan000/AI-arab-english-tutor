# Voice-Based Adaptive AI Tutor — Implementation Plan (reviewed by architect-reviewer)

## Context

The app today (verified against `docs/PROJECT_BRAIN.md`, commit `99c187f`) is a text-only, lesson-constrained Q&A tutor: one fixed difficulty (`"A1–A2 beginner"` hardcoded in `prompts/prompt_builder.py`), no accounts, no usage limits, and corrections are already bilingual but the rest of the UI is English-only. The user wants five things, clarified via questions:

1. **Voice** — fully cloud STT+TTS via Deepgram (Nova-2 for transcription, Aura for replies), turn-based ("walkie-talkie": record → transcribe → reply → speak), not live-streaming duplex.
2. **Difficulty level**, user-selected, independent of lesson topic.
3. **Natural, free-flowing conversation** instead of rigid Q&A — the agent proactively picks a topic when the learner stalls. Both the existing lesson-constrained mode **and** a new open-topic "Free Talk" mode should exist side by side.
4. **Arabic-first correction and UI** — corrections already carry an Arabic explanation; this extends that to the rest of the learner-facing chrome (labels, summary, recommendations), since the interface should read naturally to an Arabic speaker while the practice itself stays in English.
5. **Daily usage limit** to cap OpenRouter + Deepgram (STT + TTS) cost — this requires real identity, so basic email/password accounts are being added (the app currently has none).

This is a genuine architecture change (new auth surface, new data model, new external providers, new cost-control layer) touching every layer of the existing strangler-fig-migrated stack (`app.py`/`components` → `api_client.py` → `api/` → `services/` → `repositories/` → `services/database.py`). The plan below follows and extends that layering exactly — no new architectural style is introduced.

---

## A. Accounts & Auth (foundation — everything else depends on this)

- **New table** `users`: `id, email UNIQUE (stored lowercased), password_hash, display_name, created_at`.
- **New service** `services/auth.py`: `hash_password`/`verify_password` using **`bcrypt` directly** (not `passlib[bcrypt]` — passlib is unmaintained and its bundled bcrypt-detection breaks on bcrypt ≥4; reject passwords >72 bytes since bcrypt silently truncates beyond that), `create_access_token`/`decode_access_token` (JWT via `pyjwt`, 24–72h expiry, no refresh-token complexity needed at this scale). Secret comes from a new `JWT_SECRET_KEY` setting — **required, no hardcoded default**, matching how `OPENROUTER_API_KEY` is already treated as required-in-practice in `api/config.py`.
- **New repo** `repositories/user_repo.py`, following the exact thin-façade pattern of `repositories/session_repo.py:1-35` (wraps new `services/database.py` functions `create_user`, `get_user_by_email`, `get_user_by_id`; email lookups normalize to lowercase before querying, so `A@x.com`/`a@x.com` can't create duplicate accounts).
- **New schemas** `api/schemas/auth.py`: `SignupRequest{email, password, display_name}`, `LoginRequest{email, password}`, `TokenResponse{access_token, token_type, user}`.
- **New route** `api/routes/auth.py`: `POST /api/v1/auth/signup`, `POST /api/v1/auth/login`. New `AppError` subclasses in `services/errors.py` (same pattern as `LessonNotFoundError` etc.): `DuplicateEmailError` (409), `InvalidCredentialsError` (401).
  - **Login must run at constant time regardless of whether the email exists** — verify against a dummy bcrypt hash when the email isn't found, so account existence can't be inferred from response timing.
  - **Both endpoints get a per-IP+email attempt counter** (reuse the same `daily_usage`-style table pattern: `auth_attempts(ip, email, window_date, count)`) to blunt credential-stuffing against a publicly reachable login endpoint — this app has no other rate limiting today, and auth is the one surface that specifically needs it.
- **New dependency** in `api/dependencies.py` (alongside `get_session_repository`): `get_current_user(authorization header) -> User`, decodes JWT, loads via `user_repo`, raises 401 if missing/invalid/expired.
- **Protect** `chat.py`, `sessions.py`, and the new `voice.py` routes with `current_user: User = Depends(get_current_user)`. `lessons.py`/`health.py` stay public.
- **Frontend**: new `components/auth_view.py` (login/signup `st.form`s) gates `app.py`'s routing — unauthenticated users see this before the mode/difficulty picker. Token persists across refresh via a small cookie-manager component (new frontend-only dependency), read in `app.py`/`auth_view.py` only — it must **not** be imported into `api_client.py` (that would put UI-layer session state inside the HTTP client and silently break the "presentation never touches internals directly" layering this codebase enforces, which `verify_no_service_imports.py` wouldn't catch since it only checks for `services`/`repositories`/`openrouter` imports). Instead, `app.py` reads the cookie and calls a new `api_client.set_auth_token(token)` setter; `_auth_headers()` reads from that module-level state.
- **401 handling**: `api_client._request_post` (`api_client.py:87`) currently turns every failure into a generic `st.error()` + empty fallback. It must special-case 401 responses: clear the stored token, clear the auth cookie, and `st.rerun()` back into `auth_view` — otherwise an expired token just shows "temporarily unavailable" forever with no way out except a manual page reload.
- **Explicit, accepted tradeoffs** (state these to the user, don't silently skip them): Streamlit has no server-side session concept, so the JWT sits in a JS-readable cookie, not an HttpOnly one — acceptable for this low-stakes learning app, same trust model as the existing `BACKEND_URL` secret. No email verification step — signup is immediate. Both are fine for this app's stage but are real gaps, not oversights.

## B. Difficulty level + Free Talk mode

- **`difficulty`**: `"beginner" | "intermediate" | "advanced"`. Defined in a new `prompts/difficulty_levels.yaml` (same pattern as the other prompt YAMLs) — per level: vocabulary complexity, pace, and correction-strictness guidance injected into the system prompt.
- **`mode`**: `"lesson"` (existing behavior, `lesson_id` required) | `"free_talk"` (new, `lesson_id` absent). Free Talk uses a new `prompts/free_talk_context.yaml` instead of `lesson_context.yaml` — instructs the agent to pick real-world topics itself and correct any mistake, not just the one lesson's grammar point.
- **`prompts/prompt_builder.py`**: `build_messages(lesson: dict | None, history, start=False, difficulty="beginner", mode="lesson")`. Builds system content from `free_talk_context.yaml` when `mode=="free_talk"`, always appends the difficulty block regardless of mode.
- **`prompts/system_prompt.yaml`** gains one new instruction block: keep the conversation flowing like a real back-and-forth (ask follow-ups, react to what was said); if the learner stalls or says they don't know what to talk about, pick a new topic and start talking about it rather than waiting on them. This is the concrete mechanism behind "real-time conversation" — it's a prompting change, not new infra, consistent with the turn-based-voice decision.
- **`services/conversation.py`**: `start_conversation`/`send_message` gain `difficulty: str`, `mode: str` params (`lesson_id` becomes `Optional[str]`, only resolved via `lessons.get_lesson()` when `mode=="lesson"`).
- **DB**: `conversations` gains `user_id` FK, `difficulty TEXT`, `mode TEXT DEFAULT 'lesson'`; `lesson_id`/`lesson_title` become nullable (Free Talk rows store `lesson_title="Free Talk"` for display). See §D below for why `user_id` has to land here, not just on the route.
- **Free Talk must not silently break the existing save/list/detail path** — as drafted, `services/conversation.py:52`'s `end_session` calls `lessons.get_lesson(lesson_id)` unconditionally, and `models/conversation.py`'s `SessionListItem`/`SessionDetail`/`Conversation` all declare `lesson_id: str` as non-optional. Fix required in this plan, not left as a follow-up: `end_session(lesson_id: str | None, ..., mode: str)` skips the lesson lookup and uses `lesson_title="Free Talk"` when `mode=="free_talk"`; the three models above get `lesson_id: str | None`. `models/conversation.py` and `api/schemas/session.py` are therefore modified files, not just `services/conversation.py`.
- This is a `SCHEMA_VERSION` bump (2→3) — see §D's migration-strategy fix, which changes how destructive this bump is allowed to be for the new tables.
- **Frontend**: new `components/mode_picker.py` — after login: Mode (Lesson / Free Talk) → Difficulty (Beginner/Intermediate/Advanced) → if Lesson mode, existing lesson picker; if Free Talk, straight to chat start. `sidebar.py` displays mode + difficulty in Arabic.

## C. Voice pipeline (turn-based, fully cloud, Deepgram)

- OpenRouter (current LLM provider) has no audio endpoints, so voice needs a **separate Deepgram key** (`DEEPGRAM_API_KEY`, new setting) — the text conversation LLM call via OpenRouter is untouched. Deepgram covers both directions with one provider/one key: **Nova-2** for STT, **Aura** for TTS — cheaper per-minute than Whisper on the STT leg, and avoids running two separate voice providers for no real benefit.
- **New `services/voice.py`**, hand-rolled `httpx` client matching the existing `services/openrouter.py` pattern (no new SDK dependency; Deepgram's REST API doesn't need its own SDK for these two calls):
  - `transcribe_audio(audio_bytes, mimetype) -> str` — `POST https://api.deepgram.com/v1/listen?model=nova-2&smart_format=true` with `Authorization: Token {DEEPGRAM_API_KEY}` and the raw audio bytes as the request body (Deepgram takes audio directly, not multipart form-data like OpenAI's endpoint — the request-building code differs from what a Whisper integration would look like). New `VoiceTranscriptionError` (502), same family as `LLMError`.
  - `synthesize_speech(text, voice="aura-asteria-en", language="en") -> bytes` — `POST https://api.deepgram.com/v1/speak?model={voice}` with the text as JSON body, returns audio bytes directly. New `VoiceSynthesisError` (502). Aura's Arabic voice coverage should be checked against Deepgram's current model list during implementation — if no Arabic Aura voice exists yet, the Arabic correction "listen" button (see below) falls back to browser-native `speechSynthesis` for that one case only, keeping the English TTS path on Deepgram.
- **New route** `api/routes/voice.py`: `POST /api/v1/voice/transcribe` (browser records WAV/webm, uploaded as multipart from Streamlit → FastAPI reads the raw bytes off the upload and forwards them as Deepgram's request body → `{text}`), `POST /api/v1/voice/speak` (`{text, language}` → raw audio bytes from Aura, passed straight through). Both auth-protected. `_request_post` in `api_client.py` only sends JSON today — it needs a dedicated multipart-upload helper for transcribe and a raw-bytes-response helper for speak, not an overload of the existing JSON path.
- **`api_client.py`**: `transcribe_audio()`, `synthesize_speech()`.
- **Frontend recording**: new dependency `streamlit-mic-recorder` (push-to-talk button, returns WAV bytes) added in `components/chat.py` alongside the existing `st.chat_input()` (kept as an accessibility/fallback path, not removed). Flow: record → `transcribe_audio()` → same `send_message()` call used today → reply text → `synthesize_speech(reply, "en")` → `st.audio(..., autoplay=True)`.
- **Correction cards** (`components/correction_card.py`) gain a "🔊 استمع" button per correction that plays the Arabic explanation via `synthesize_speech(text, "ar")` — directly reuses the same endpoint, ties the voice and Arabic-localization requirements together with no extra infra.
- **Voice endpoints must be metered independently — this is not optional.** `/voice/speak` is directly reachable (the correction-card listen button calls it outside any chat turn), and `/voice/transcribe` is billed per audio minute. Bundling their cost under the per-turn text limit only holds if they're unreachable outside a turn, which they aren't — a user repeatedly tapping "استمع" buys unbounded TTS with zero counter movement. Fix: `daily_usage` gets a second counter, `voice_call_count`, incremented by `services/voice.py`'s callers on every transcribe/speak call, checked against its own `DAILY_VOICE_CALL_LIMIT` setting. Additionally cap request size at the schema layer: reject audio uploads over ~10MB/60s and TTS input over ~500 characters (corrections are short; this doesn't constrain legitimate use).

## D. Daily usage limit (and closing the session-ownership gap auth introduces)

- **Auth without ownership is a data leak, not just a missing feature.** `conversations` currently has no owner column, and `SessionRepository.list_recent()` / `get_summary()` are global across all sessions. Simply gating `api/routes/sessions.py` behind `Depends(get_current_user)` (as originally planned) would make every logged-in user able to list and open *every other user's* transcripts — an IDOR on `GET /sessions/{id}`. This plan therefore requires, not defers: `conversations.user_id` FK (already added in §B's schema change), `end_session`/`SessionRepository.save` threading `user_id` through, and `list_recent`/`get_summary` filtering by the authenticated `user_id` — ownership enforced at the repository/query level, not just at the route.
- **New table** `daily_usage`: `id, user_id, usage_date TEXT, message_count INTEGER, voice_call_count INTEGER, updated_at`.
- **New settings**: `DAILY_MESSAGE_LIMIT` (default **20**, not 40 — see cost note below) and `DAILY_VOICE_CALL_LIMIT` in `api/config.py`.
- **New `services/usage.py`**: `check_and_increment(user_id)` for text/LLM turns, `check_and_increment_voice(user_id)` for transcribe/speak calls (see §C) — both raise a new `DailyLimitExceededError` (429, Arabic-first message, remaining-count included in the body) when at limit.
- **Bound the cost per turn, not just the turn count.** As drafted, `ChatMessageRequest` has no cap on message-history length or per-message content length, and the client resends full history every turn — so "N messages/day" understates real cost since prompt size grows quadratically across a long session. Add `max_length` on the `messages` list (e.g. 100) and on `Message.content` (~2000 chars) in `api/schemas/chat.py`, plus a trailing-window truncation in `prompt_builder.build_messages` so very long sessions don't silently blow past the cost model below.
- **Rough cost sanity check** at `DAILY_MESSAGE_LIMIT=20` with the above bounds: ballpark $0.12–0.18/user/day across LLM (OpenRouter) + Deepgram Nova-2 STT + Aura TTS — roughly $4–5/user/month, a deliberately conservative starting default that's just an env var to raise later. Deepgram's per-minute STT pricing is somewhat below Whisper's, so this is if anything a slight improvement over the original estimate.
- **`repositories/usage_repo.py`**, same façade pattern as `session_repo.py`; new `get_usage_repository()` DI in `api/dependencies.py`.
- **New endpoint** `GET /api/v1/usage/today` — the sidebar's "remaining messages today" display needs a real source; client-side counting would drift across devices/tabs. The 429 error body also includes the remaining count (which will be 0) for consistent display.
- **Frontend**: sidebar shows remaining messages today via the new endpoint; hitting the limit surfaces the Arabic 429 message (same error-handling path `api_client.py` already uses for other failures) and disables further input for the day via a session-state flag.

## E. Migration-strategy fix (required — accounts must not be droppable data)

`services/database.py`'s existing migration strategy is unconditional: `_needs_migration()` triggers `_drop_tables()` on any `SCHEMA_VERSION` bump, recreating `conversations`/`messages`/`grammar_feedback` from scratch. That's an acceptable tradeoff *today* because those tables hold disposable practice transcripts. It stops being acceptable the moment `users` and `daily_usage` exist in the same database: a future unrelated schema bump (v3→v4, made for some other reason entirely) would silently delete every account and password on next boot, locking every user out with no recovery path. This is a correctness gap in the plan as originally drafted, not just a nice-to-have:

- `users` and `daily_usage` are created with `CREATE TABLE IF NOT EXISTS` and are **excluded** from `_drop_tables()`.
- `_needs_migration()`'s existence/version check is split so the destructive recreate path only ever applies to the three conversation-history tables; `users`/`daily_usage` get their own additive-only migration path (new columns via `ALTER TABLE ... ADD COLUMN`, never a drop).
- This is a small, targeted change to `services/database.py` — not a switch to a migration framework (Alembic etc. is out of scope for this app's size).

## F. Arabic-first UI localization

- Scope: all learner-facing chrome (buttons, headers, sidebar, summary, recommendation text) → Arabic. The English-practice content itself (chat messages, lesson examples) stays English — that's the point of the app. Corrections already carry both languages; Arabic becomes the visually primary explanation.
- `services/scoring.py`: replace the two hardcoded English recommendation strings with Arabic ones.
- `components/*.py`: replace hardcoded English strings in place. No i18n/translation-layer framework — this app has one audience and one target language for the UI, so a full i18n system would be unused abstraction (YAGNI), consistent with existing project conventions.
- Small scoped RTL CSS (`direction: rtl; text-align: right`) applied only to Arabic-text containers (sidebar, summary, correction card's Arabic block) — deliberately **not** applied app-wide, since chat bubbles and mic controls should stay LTR.

## H. Build sequence

1. **Accounts & auth (A)** — foundation, including rate limiting and 401 handling from the start (not bolted on later).
2. **Migration-strategy fix (E)** — must land *before* or *alongside* step 1's `users` table, not after; the whole point is that `users` is never created under the droppable path.
3. **Difficulty + Free Talk mode (B)**, including the session-ownership fix (D's `user_id` threading) — still text-only at this point.
4. **Daily usage limit (D)** — text-turn limiting, history-length caps, and the `/usage/today` endpoint.
5. **Arabic UI localization (F)** — independent, can run alongside 3/4.
6. **Voice pipeline (C)** — layered on top last, reuses the chat endpoints from step 3 and the usage-limiting infra from step 4 (this is why voice comes after usage, not before — the voice-specific counters in §C depend on §D existing).
